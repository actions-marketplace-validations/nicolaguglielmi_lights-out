GO / NO-GO · v0.6.0 · Apache-2.0

Your AI agents ship code. Who checks it?

Tests pass and CI is green, yet nobody verified that those tests prove anything. lights-out judges every pull request an agent opens with numbers, not opinions: the new tests must fail without the change, the mutants on the changed lines must die, nothing may leave the ticket's files. What passes takes 5% of the traffic, rolls itself back on errors, and waits for one human GO before 100%. With Claude Code, Codex or Gemini CLI at the keyboard.

Try it: ./go demo

Runs complete on your laptop: no account, no API key, no cloud.

  1. 01 · TICKET

    A ticket draws the perimeter.

    It starts as a request: a few lines in the console's editor or ./go request. The product role asks what is missing, you answer, and the spec gate lets it through only with Given/When/Then criteria and a ## Perimeter listing the files the change may touch.

    Every path the agent changes must match it, checked before a pull request exists. One file outside, and no PR is ever opened.

    core/perimeter.sh
  2. 02 · SIX ROLES

    Six roles, each in its own box.

    One role writes code, in a throwaway sandbox with a token for that role only. The others confirm the ticket, read risky diffs, brief the human and watch production. Each has its own prompt and budget.

    Your model, your coding CLI: Gemini, Claude or OpenAI, through gemini-cli, claude-code or codex, all behind the same guard.

    roles/ · core/crew.sh
  3. 03 · EIGHT GATES

    Eight gates judge every pull request.

    Risk, secrets, weakened tests, dependencies, static analysis, tests, mutation, and proof that the new tests fail without the change. Each prints one line, GO or NO-GO with the reason, and every threshold says where it comes from. The first NO-GO stops the rest.

    A PR is judged by its base's policy, never its own: it cannot edit the gates that judge it. A test written to pass does not get through: dropping an assertion is a NO-GO, mutation testing catches a test that checks nothing, and a new test that already passes on the base proves nothing.

    gates/ · docs/adr/0033 · docs/adr/0053
  4. 04 · THE CANARY

    A signed canary, judged by numbers.

    One signed image per merge takes 5%, then 25% of real traffic. One PromQL file compares it with stable on errors and p95 latency.

    A bad number rolls it back with nobody paged. So does a query that cannot be answered, and the line says cannot judge, not a verdict. No model decides whether a canary is healthy.

    verify/slo.promql · core/launchpad.sh
  5. 05 · ONE HUMAN

    One human turns the lights back on.

    The step to 100% waits for a person's GO, after a brief built from the release record. NO-GO rolls back.

    Silence never promotes: with no answer, nothing moves.

    core/promote.sh

The console

From the request to the release, on one page.

A request comes in, the product role asks what is missing, a person answers, the spec gate checks the criteria, and only then does an agent start. The console shows every ticket on that path, from one versioned document, the logbook, and is a place to work: a request is written there and checked by the spec gate as it is typed, and the project's decisions are searched there. It has three writes, a new request, the answer to an open question and go-for-launch, each recorded with who pressed. Light or dark, as you choose.

The stills are the real console, rendered in CI over the logbook its tests build (fixtures/logbook/golden-1.5.json), which holds tickets in more states than one demo leaves; its model is a stub. The ADR search reads a logbook built in CI from this repository's own project map.

README · what is recorded
Plainly

What is real, and what is recorded.

Real

The gates, the signed build, the canary, the metrics, the rollback, the audit chain, GitLab as a code host (./go gitlab-conformance), Jenkins as a surface that shows the gates' line and never judges (./go demo-jenkins), adapters outside the repository admitted by a conformance proof, each release's signed evidence pack with the console frozen beside it (./go evidence), the delivery measures (./go dora) and the cost of every run with a budget that stops the next attempt (./go spend), both on the console's overview. The provider scoreboard (./go scoreboard): ten tenacity tickets run live on Anthropic and on Gemini, NO-GOs and budget stops included, each row naming the handoff and run it comes from. Nothing in them is simulated.

Recorded

Without a key the agents replay answers recorded once against the Gemini API; with a key and PROFILE=l1 they run live. The videos on this page are the board's scripted walks, with example versions and numbers. The frozen console is a real ./go demo run at L0, so its agents replayed recorded answers; the gates, the canary and the rollback in it are real.

Not yet

One codebase not written for lights-out so far, tenacity: ten small, low-risk tickets, so no review and no human gate ran, and each was run once per provider. OpenAI was not run. Outside adapters are proven for a StateStore only. Jenkins is proven with Jenkinsfile Runner, not a real controller. The full tower on GitLab does not fit beside the plane.

Try it

Watch a canary roll itself back.

You need podman (or Docker on Linux) and git. Nothing else on your machine.

The demo

An agent turns a ticket into a pull request, eight gates judge it, it merges, builds, signs and takes 5% of the traffic. Verify sees the errors and rolls it back on its own. The run ends with GO: demo.

$ git clone https://github.com/nicolaguglielmi/lights-out.git
$ cd lights-out
$ ./go demo

First run 10–15 minutes (it downloads about 1.2 GB and builds the toolchain), then about 7. Installing podman →

Gates on your repository

On every pull request, from the Action on the Marketplace. With no .lights-out/ contract yet, its first check is NO-GO and carries one drafted from your base, with the two commands that commit it.

permissions:
  contents: read
  checks: write
steps:
  - uses: actions/checkout@v7
    with:
      fetch-depth: 0
  - uses: nicolaguglielmi/lights-out@v0.6.0

The lights-out wrapper runs init and the gates from the same image, inside your repository, without cloning lights-out.

$ mkdir -p ~/.local/bin
$ curl -fsSL -o ~/.local/bin/lights-out https://raw.githubusercontent.com/nicolaguglielmi/lights-out/v0.6.0/lights-out
$ chmod +x ~/.local/bin/lights-out
$ cd ~/code/your-repo
$ lights-out doctor    # engine, image, key: one line each
$ lights-out init      # drafts .lights-out/ outside your repository
$ cp -R ~/.local/state/lights-out/your-repo/.lights-out/. .lights-out/
$ git add .lights-out && git commit -m "add lights-out contract"
$ lights-out gates     # judges the last commit

Image ghcr.io/nicolaguglielmi/lights-out-gates:0.6.0, amd64 and arm64, 508 MB unpacked, signed keyless with Sigstore: verify it, or pin it by digest. test-proof and test-integrity are also Actions of their own.

No engine at hand? uvx lights-out-gates --light runs the gates that need only git and Python, in under a second, and names the ones it did not run.
