# 0002 — Gemini CLI 0.59.0 does not serve `gemini-3.8-flash`, contradicting plan §5

- Status: open
- Labels: platform, roles/, adapters/gemini-cli, M5 finding, decision needed before M6
- Found: 2026-09-15, recording ticket 0001's fixture at M5 (docs/adr/0017)

## Problem

Plan §5 commits to `gemini-3.8-flash` for every role. `docs/adr/0017`'s
pinned worker (`adapters/gemini-cli/package.json`,
`@google/gemini-cli@0.59.0`) requests that model — `-m gemini-3.8-flash`,
the fully-qualified `-m models/gemini-3.8-flash`, and `settings.json`'s
`model.name` were all tried — and CLI 0.59.0 silently serves
`gemini-3.5-flash` instead, on every channel, with no warning. The model
itself is real and reachable with this project's key, confirmed directly
against the Gemini API's own model-list endpoint
(`GET https://generativelanguage.googleapis.com/v1beta/models`, which
lists `models/gemini-3.8-flash`); the CLI is what does not route to it.

`fixtures/0001/dev-worker/`, M5's one recorded fixture, is therefore
recorded against `gemini-3.5-flash`, not the model the plan names.

## Root cause, verified 2026-09-15

`fix(core): preserve explicit versioned Flash model IDs`
(google-gemini/gemini-cli#29252, merged 2026-09-09, one day after
0.59.0's release): "Preserve explicit versioned Flash model IDs instead
of silently remapping them to the Gemini 3.5 Flash rollout default."
This is the exact bug, confirmed by the CLI's own maintainers, not
inferred. It ships in the nightly line from `0.61.0-nightly.20260909`
onward; no stable release contains it yet — `v0.59.0` is still `Latest`
on GitHub as of 2026-09-15. Nightlies are published to the npm registry
under their own permanent, exact version strings (not only as GitHub
release assets), so pinning one the same way `package-lock.json` already
pins `0.59.0` is mechanically possible without any adapter change.
Verified live: `0.61.0-nightly.20260915.g9c1b0a610` installed standalone
and probed with the same non-agentic call used to find the original bug
(`gemini -p "Reply with exactly: OK" -m gemini-3.8-flash --approval-mode
yolo --skip-trust --output-format json`) reports
`stats.models: {"gemini-3.8-flash": {...}}` — the fix works, live, with
this project's key.

## Three options, in the order the finding session ranked them

1. **Bump the CLI pin** to a nightly (or, once one exists, a stable
   release) that contains PR #29252. Keeps plan §5's model choice.
   Against CLAUDE.md's pinning rule ("pinna tutto... rinnovi solo con un
   commit dedicato che fa passare gli eval"): a nightly is not the stable
   channel this repo has pinned everything else to, and a pin renewal
   needs its own eval-gated commit, not a byproduct of this ticket.
2. **Correct the plan to `gemini-3.5-flash`.** Honest about what 0.59.0
   actually serves, no pin change. Against: throws away plan §5's own
   stated reasoning for choosing 3.8 specifically ("il modello Flash più
   capace, pensato per software engineering a lungo orizzonte e agenti
   autonomi").
3. **Route through Vertex AI instead of the Gemini API key.** Untested
   whether Vertex's model resolution has the same bug — Vertex is a
   different backend the CLI's `AuthType.USE_VERTEX_AI` path may or may
   not share this remapping logic with. Against: Vertex is L2+ in plan
   §3's table (a GCP project with billing), and L1's whole point is a
   free-tier key with no account beyond it; moving the default worker
   there for every role would need its own golden-rule check.

## Acceptance criteria

Given the three options and the verification above
When the decision is made
Then it is recorded as an ADR (numbered after 0017), with the rejected
alternatives and their reasons, same as every other structural decision

Given whichever option is chosen
