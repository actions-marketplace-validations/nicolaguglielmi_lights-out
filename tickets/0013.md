# 0013 — Unknown venue answers 500 (the rework demo's ticket: ticket 0001's bug, judged twice)

- Status: open
- Labels: bug, app/backend, M15 (rework loop demo)
- Found: 2026-11-03, designing `./go demo-rework` (docs/adr/0038 §10)

## Problem

This is ticket 0001's bug, restated as the subject of `./go demo-rework`.
`meetups/geocoder_client.py` only handles a geocoder status `>= 500`; the
fake geocoder answers `404` for a venue it does not know, the client
calls `response.json()` on it, and `POST /api/meetups` ends as an
unhandled `500` instead of one of the two documented outcomes.

Ticket 0001 stays the golden path's ticket: its recorded fix passes the
gates first time. This ticket exists so the rework loop has a subject
whose first attempt does not pass, with its test in `test_meetups.py`,
where the committed `fake-test` and `honest-fix` gate fixtures put it.

## Acceptance criteria

Given a venue that no geocoder example knows
When a logged-in user posts it to `POST /api/meetups`
Then the response is `201` with `venue_lat` and `venue_lon` both `null`
(a 404 from the geocoder is "no result", as a real Nominatim's `200 []`).

Given that outcome
When the contract test suite runs (`./go test`)
Then `app/contracts/geocoder/examples.json` contains a 404 example for an
unknown venue, and a test posts that venue and asserts the `201` and the
null coordinates — a test that fails without the fix.

Given `./go up` and `./go smoke`
When the smoke posts `Milano, Duomo`
Then it still returns `201` with non-null coordinates.
